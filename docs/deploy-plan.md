# 公開の計画（D案：今のサーバーの入口に、静的サイトを置く）

## 方針
- ドメイン（DNS）は変えない。`/kdhs/`（別のWordPress、約5.5GB）は、そのまま。
- GitHubを元データの保管場所にする。サーバーへの転送は、GitHub Actions（`.github/workflows/deploy.yml`）を、手動で実行する。
- 転送は「追加と上書き」だけで、削除はしない。サーバー側のファイルは、勝手には消えない。

## 注意
- 入口の WordPress と `/kdhs/` の WordPress は、別のものとして、扱う。`/kdhs/` の中身は、触らない。

## 公開時に決めておくこと
1. `backups` の中身。バックアップのファイルが、誰でも取れる場所にあれば、危険。先にサーバー外へ移し、公開フォルダから外す。
2. `pkss`、`pics`、`pdf`、`kss`、`ksa`、`kda` の用途。外部からリンクされている可能性があるため、**触らない**。
3. 入口の `index.php` は、削除せず、`index.php.bak` に名前を変える（または `.htaccess` の `DirectoryIndex` で、`index.html` を優先する）。元に戻せるようにする。
4. 入口の `wp-config.php`（データベースの接続情報）、`wp-login.php`、`xmlrpc.php`、`readme.html`、`license.txt` は、公開後に、アクセスできないようにする（まず `.htaccess` で止める。数週間後に、削除を検討）。

## `backups` フォルダの確認結果（2026-11-18）
- 中身は、サーバー移行時の、古いサイトのファイル（92個、約4MB）。PHPファイル（`top.php`、`recruit.php`、`reunion.php`、`routing.php` など）、メール送信用とみられる `postmail`、`class` フォルダなどがある。
- **公開フォルダの中にあるPHPは、URLを直接開かれると、実行される。** メール送信の仕組みが入っていれば、迷惑メールの踏み台に、悪用される恐れがある。
- ユーザーの判断：不要。
- 対応：(1) まず `backups` に、アクセスを禁止する `.htaccess` を置く（すぐ元に戻せる）。(2) サーバー全体のバックアップを取った後で、パソコン（GitHubではない場所）に4MBの控えを保存して、サーバーから削除する。(3) 同じ性質の古いフォルダ（`pkss`、`kss`、`ksa`、`kda`、`pics`、`pdf`）に、PHPファイルがないか、確認する。

## 入口の `.htaccess` の確認結果（2026-11-18）
- 中身は、SVGの設定2行と、WordPressの標準の転送規則（重複して2回）だけ。独自の転送・制限・認証は、ない。
- 公開時に、置き換える（`deploy/htaccess-root.txt`）。**WordPressをやめると、http から https への転送（Really Simple SSL が担っていた可能性が高い）が、なくなる**ため、新しい `.htaccess` で補う。
- 確認事項：`/kdhs/` に、それ自身の `.htaccess` があること。`/kdhs/` が、入口の転送規則に頼っていないこと。
- 確認事項：`www.kurume-dental.or.jp` が、今のサイトで使われているか。使われていれば、https と www の扱いを、あらためて決める。

## `/kdhs/` の `.htaccess` の確認結果（2026-11-18）
- 自分自身の転送規則（`RewriteBase /kdhs/`、`/kdhs/index.php`）と、https への転送（Really Simple Security）を持っている。**入口の転送規則には、頼っていない。** 入口の `.htaccess` を置き換えても、転送規則は、影響を受けない。
- ただし、入口の設定のうち、`DirectoryIndex`、`Header`、`ErrorDocument`、`Options` などは、`/kdhs/` に引き継がれる。
- 発見：入口の `DirectoryIndex` を `index.html` だけにすると、`/kdhs/` の入口（`index.php`）が、表示されなくなる。→ `DirectoryIndex index.html index.php` にして、解決した。
- 公開後の確認項目：`https://kurume-dental.or.jp/kdhs/` が、これまでどおり表示されること（トップ、下層ページ、ログイン画面、管理画面のURLを、学校の担当者に確認してもらう）。

## 転送方法の選択（2026-11-18）
- 転送専用のFTPアカウントは、作れない。使えるのは、管理用アカウント（サーバー全体に書き込める）だけ。
- 案A：GitHub Actions（自動）。管理用の認証情報を、GitHubの Secrets に預ける。守りを固める必要がある（GitHubアカウントの二段階認証、Environments の承認者と、デプロイできるブランチの限定、パスワードの変更）。
- 案B：手動（WinSCPの「同期」）。GitHub Desktopで最新（main）を取り込み、WinSCPで、公開用のファイルだけをサーバーへ送る。認証情報は、パソコンの中だけに残る。更新が少ない静的サイトには、向いている。
- 当面のおすすめ：案B。自動化は、あとから、守りを固めて、検討する。

## サーバー会社の「Webユーザー」について（2026-11-18、ユーザーが確認）
- Webユーザーは、複数のお客さまが、それぞれ自分のホームページを持つためのアカウント。
- 制限：**ドキュメントルート（入口）へのコンテンツ設置は不可**。CGI・PHPは利用不可。FTPは利用可能。
- 結論：入口に新サイトを置く用途には、使えない。入口への転送は、管理用アカウントだけ。→ 案B（手動転送。認証情報は、パソコンの中だけ）が、当面の既定。

## バックアップの計画（2026-11-18）
- 全体を、FTPでダウンロードするだけでは、足りない。WordPressの内容（設定、利用者、投稿）は、**データベース**にあり、FTPのファイルには、含まれない。
- 入口への転送で、**書き換わる・名前が変わるもの**は、少ない。だから、次の「対象を絞ったバックアップ」で、実際のリスクに備えられる。
  1. 入口の `.htaccess`、`index.php`、`wp-config.php`（データベースの接続情報。**保管に注意**）
  2. `wp-content/themes/spacious-child/`（約8.5MB。新サイトの部品で上書きされる）、`wp-content/themes/spacious/style.css`
  3. （任意）`wp-content/uploads/` の、新サイトが使う13フォルダ
  4. 入口のWordPressの**データベース**の書き出し（phpMyAdmin、またはAll-in-One WP Migration）
- `/kdhs/` は、書き換えない。学校の担当者が、自分たちのバックアップを、持っているかを確認する。
- サーバー会社の、サーバー全体のバックアップ（頻度、保存期間、戻し方、費用）を確認する。
- バックアップには、パスワード類（`wp-config.php`）が含まれる。**GitHubに置かない。** 公開が落ち着いたら、安全に削除する。
- 入口のWordPressの本体は、公開時に**削除せず、名前を変えるだけ**にする。元に戻すのは、名前を戻すだけ。

## メールへの影響の確認（案B・C：ウェブをGitHub Pagesへ移す場合）
- ウェブの向き先（A、AAAA、CNAME）と、メールの配送先（MX）は、別の記録。ウェブだけを変えれば、メールは、原則として、影響を受けない。
- 事前に、DNSの全記録の一覧を入手して、次を確認する。
  1. MXの値が、入口のドメイン自体（`kurume-dental.or.jp`）を指していないか。指していると、Aレコードの変更で、メールが止まる。メールサーバーに専用の名前（例：`mail.…`）があれば、それを使う。
  2. SPF（TXT）が、`a` や `mx` で、入口のドメインのAレコードに頼っていないか。頼っていれば、IPアドレスを直接書く形に直す。
  3. ウェブメール（例：`/webmail`）が、入口のドメインの下にないか。あれば、別の名前（サブドメイン）へ移す。
  4. DKIM、DMARC、メールソフトの接続先の名前（受信・送信サーバー）。
- 今のサーバーの契約は、メールを使う間は、解約しない。メールを別のサービスへ移す場合は、先に移して、安定してから、ウェブを移す。
